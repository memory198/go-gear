# go-gear 架构文档

> 本文讲解 go-gear 各模块的**职责**、**核心功能**与**协作关系**，帮助开发者理解整体设计。
> 使用层面请参考 [使用指南](使用指南.md)；各方案开发记录见 [方案概览](dev/方案概览.md)。

## 一、总体定位

go-gear 是一个 **Go Web 服务工具集**，由 6 个可独立或组合使用的包构成：配置、带堆栈错误、泛型 HTTP Handler、结构化日志、请求上下文、中间件。它**不绑定路由库**（推荐搭配 chi），**不强制接入 OTel**，每个包都可以单独拿出来用。

## 二、架构总览

```
┌──────────────────────────────────────────────────────────────┐
│                      业务代码（你的 service / handler）        │
└──────────────────────────────┬───────────────────────────────┘
                               │
        ┌──────────────────────▼──────────────────────┐
        │              framework (HTTP 胶水层)          │
        │  Handler[Req,Res] / Handle / HandleContext   │
        │  Bind → Validate → 业务 → WriteOK/WriteError │
        │  Context = gctx.Context（别名再导出）         │
        └───────┬──────────────────────────┬───────────┘
                │                          │
   ┌────────────▼───────┐      ┌───────────▼──────────────┐
   │  middleware (可选)  │      │        gctx              │
   │  Logger / Recoverer │      │ 请求上下文：trace/span   │
   │  OTel               │      │ 超时/取消/值存储          │
   └────────────┬────────┘      └───────────┬──────────────┘
                │                           │ 引用 key 契约
   ┌────────────▼────────┐      ┌───────────▼──────────────┐
   │     logger          │◄─────│   定义 Root/Middle/       │
   │ 默认实例/双编码/滚动 │       │   Current 三个 trace key  │
   └─────────────────────┘      └──────────────────────────┘

   errors（带堆栈错误）    ← 纯工具，谁都不依赖，业务代码直接替换标准库
   config（配置管理）      ← 独立包，只依赖 yaml/fsnotify
```

### 依赖关系一览

| 包 | 依赖（项目内） | 依赖（第三方） | 可独立使用 |
|---|---|---|---|
| `errors` | 无 | 无 | ✅ |
| `config` | 无 | yaml.v3、fsnotify | ✅ |
| `logger` | 无（只定义 trace key 契约） | 无 | ✅ |
| `gctx` | logger（仅引用 3 个 key 常量） | 无 | ✅（需编译 logger） |
| `framework` | gctx | go-playground/validator | ✅ |
| `framework/middleware` | framework、logger | otel SDK | ✅ |
| 业务代码 | 以上任意 | — | — |

## 三、模块职责总览

| 模块 | 一句话职责 | 核心文件 |
|---|---|---|
| **errors** | 带调用堆栈的错误处理，兼容标准库 | errors.go / error.go / stack.go / api.go |
| **config** | YAML 配置加载 + 热重载 + 类型安全访问 | config.go / hotreload.go / value.go |
| **logger** | 五级结构化日志（text/JSON、文件滚动、trace 字段） | logger.go / default.go / encoder.go / writer.go / trace.go |
| **gctx** | 请求级上下文：追踪、span 链、超时、值存储 | ctx.go |
| **framework** | 泛型 Handler 的 HTTP 适配（绑定/校验/统一响应） | handler.go / bind.go / response.go / error.go / context.go |
| **middleware** | HTTP 横切关注点：访问日志、panic 恢复、OTel | logger.go / recover.go / otel.go |

## 四、各模块详解

### 4.1 errors —— 带堆栈的错误

**职责**：把"错误发生在哪"变成一等公民。业务代码**直接替换标准 errors 包导入**即可获得堆栈能力。

**核心设计**：

- `withStack{msg, cause, stack}`：`Unwrap()` 透传 cause，所以 `errors.Is/As` 沿标准错误链穿透，与标准库完全兼容
- 捕获堆栈时**过滤 runtime 和 errors 包自身的帧**，保留业务调用点；深度限 8，避免噪音
- `fmt.Sprintf("%+v", err)` 打印完整错误链，最底层原因先出，每层带 `at file:line (func)`

**API**：`Errorf` / `Wrap` / `Wrapf` / `WithStack`（只记堆栈不加描述）/ `From`（防重复包裹）/ `FromMsg` / `Stack`

**边界**：不与 framework 的 `BizError` 强绑定——`BizError` 是独立类型，但 `WriteError` 用 `errors.As` 能在带堆栈的包装下找到它，两者天然兼容。

### 4.2 config —— 配置管理

**职责**：从 YAML 加载配置，支持文件合并、环境变量覆盖、目录热重载。

**核心功能**：

1. `Load(configFile)` 三步：解析入口文件（支持 `include` 递归合并多个文件）→ 转成 `Config` 结构体（默认值兜底）→ 环境变量覆盖（`APP_*`）
2. **重复 key 直接 panic**：配置冲突显式失败，避免静默覆盖
3. `Watcher`：基于 fsnotify 监听配置目录，`Watch("server.addr")` 按路径订阅变化，推送到 channel
4. `Value`：链式类型安全访问（`.String()` / `.Int()` / `.Bool()`，支持默认值）

**边界**：注释宣称"命令行 flag 覆盖"，当前版本**尚未实现**（优先级实际为 文件 < 环境变量）。

### 4.3 logger —— 结构化日志

**职责**：输出带级别、调用点、trace 链路字段的日志，text（人读）与 JSON（机器采集）双格式，支持控制台 + 文件双输出。

**核心设计**：

1. **默认实例 + 包级函数**（`default.go`）：`logger.Info(ctx, ...)` 开箱即用；`SetDefault` 可整体替换；`atomic.Pointer` 保证线程安全
2. **五级日志**：DEBUG/INFO/WARN/ERROR/FATAL（FATAL 输出后 `os.Exit(1)`）
3. **trace 三元组**：`RootTraceID` / `MiddleSpanIDs` / `CurrentSpanID` 是日志与追踪体系对接的**唯一契约**（见 §五）
4. **双编码器**（`encoder` 接口）：text 只显示 root_trace_id（控制人读噪音）；JSON 完整携带三元组，`middle_span_ids` 为数组
5. **输出管理**：console 与 file 可同时存在；按天滚动；`MaxAge` 自动清理过期文件（文件名前缀隔离多实例）
6. **caller 定位**：遍历调用栈跳过 logger 包内部帧，输出相对路径:行号，不受内联影响

**边界**：刻意**不提供 kv 字段 API**（如 `slog` 风格），维持 `Info(ctx, msg)` 简洁签名。日志结构化定位主要由 trace 字段 + JSON 格式承担；若未来需要字段级检索，计划迁移标准库 `log/slog` 底层。

### 4.4 gctx —— 请求上下文

**职责**：提供标准 `context.Context` 不具备的请求级能力：追踪、span 链、超时控制、值存储。

**核心设计**：

1. **结构**：内嵌标准 context（只用于超时/取消传播）+ `parent` 指针（用于 value 回溯，形成**父链**）
2. **追踪字段**：`traceID` / `spanID` / `parentSpanID` / `middleSpanIDs`，全部 `crypto/rand` 生成 **OTel 兼容 hex 格式**（trace 32 位、span 16 位）
3. **入口提取**：`NewContext` 优先解析 W3C `traceparent` 头，`X-Trace-ID`/`X-Span-ID` 兜底，无则自动生成
4. **派生**：`StartSpan`（新 spanID，旧 spanID 推入中间链）/ `WithTimeout(Func)` / `WithDeadline` 创建子 Context，共享父链
5. **值存储**：`Set(key, value)`（string key，重复 panic）——**派生上下文不继承父层 values**，可自由覆盖；`Value` 读取顺序：logger 的 trace key → 本层 values → 沿 parent 链回溯 → 内嵌标准 context
6. **与 logger 的对接**：`Value()` 中识别 logger 的三个 key 并**动态返回自身字段**——`MiddleSpanIDs()` 从父链实时聚合，派生上下文无需维护

**边界**：values 仅支持 string key；追踪为轻量内置方案，不替代 OTel（两者关系见 §五）。

### 4.5 framework —— HTTP 胶水层

**职责**：定义业务 Handler 的签名约定，并把"绑定 → 校验 → 业务 → 统一响应"的样板流程封装掉，输出标准 `http.HandlerFunc`。

**核心设计**：

1. **两个泛型签名**：`Handler[Req,Res]`（标准 context）与 `ContextHandler[Req,Res]`（`*gctx.Context`），编译期类型安全，Req/Res 即入参出参模型
2. **两个包装函数**：`Handle` / `HandleContext` 内部流程完全相同（见 §六），唯一区别是后者先 `gctx.NewContext` 造带追踪能力的上下文
3. **`Context` 是 gctx 的类型别名**（`type Context = gctx.Context`），不是包装——gctx 能力原样可用，framework 只做再导出
4. **绑定**：`Binder` 接口是扩展点（可混合 URL/Query/Body 自定义绑定），默认只解析 JSON body
5. **校验**：validator 配置为按 **json tag** 报错，错误信息对前端友好
6. **统一响应**：`{code, message, data}`，`WriteError` 用 `errors.As` 识别 `BizError`（取业务码 + HTTP 状态码），其余错误统一 500

**BizError**：`{HTTPStatus, Code, Message}` + `WithMsg`（不可变返回新错误），预定义 6 个：400/401/403/404/409/500。

**边界（刻意不做）**：不做路由、不做方法匹配、不提供中间件链注册（middleware 是"函数包函数"嵌套风格）。指南推荐搭配 chi 使用。

### 4.6 middleware —— HTTP 横切关注点

| 中间件 | 职责 | 说明 |
|---|---|---|
| `Logger` | 访问日志：方法/路径/状态码/耗时 | 用标准库 `log.Printf`（尚未接入 logger 包，见遗留问题） |
| `Recoverer` | 捕获 handler panic，记堆栈并返回 500 | 防止单请求崩溃拖垮进程 |
| `OTel(serviceName)` | W3C traceparent 提取 → 创建 Server Span → 桥接 logger 链路字段 → 记录状态码属性 | 开发者无需改业务代码 |

**OTel 桥接**：中间件从 OTel span 取出 trace/span ID，通过 `logger.WithRootTraceID` / `WithCurrentSpanID` 写入 context，后续所有 `logger.*` 输出自动带字段。OTel SDK 由调用方配置（Jaeger/OTLP），logger/gctx 本体零 otel 依赖。

## 五、跨模块协作：trace 链路如何贯通

这是全库最关键的协作设计，核心是 **"logger 只读、数据方动态提供"的 key 契约**：

```
logger 定义契约（只读）                     数据提供方（按场景二选一）
┌────────────────────────┐        ┌─────────────────────────────────┐
│ RootTraceIDKey         │◄───────│ gctx.Context.Value()：            │
│ MiddleSpanIDsKey       │        │   动态返回自身 traceID/spanID，   │
│ CurrentSpanIDKey       │        │   middleSpanIDs 从 parent 链聚合  │
│                        │        ├─────────────────────────────────┤
│ traceFromCtx(ctx) 读取 │◄───────│ middleware.OTel：                │
│                        │        │   WithRootTraceID /              │
└────────────────────────┘        │   WithCurrentSpanID 注入 context │
                                  └─────────────────────────────────┘
```

- **不接 OTel**：用 `framework.HandleContext`，业务拿到 `*gctx.Context`，logger 读 key 时由 gctx 动态提供（含中间 span 链）
- **接 OTel**：`middleware.OTel` 在 context 中注入 OTel 的 ID，logger 直接读取；此时建议用 `Handle`（标准 context），避免与 gctx 自生成 ID 冲突

> ⚠️ 两套 ID 来源并存：上游无 `traceparent` 时，gctx 与 OTel 各自生成 ID 可能不一致。**用法约定：接 OTel 的入口用 `Handle`；不接 OTel 用 `HandleContext`**（详见 dev/2026-09-02 遗留问题）。

## 六、跨模块协作：一次请求的生命周期

```
HTTP 请求
  │
  ├─[可选] middleware.Logger / Recoverer / OTel     ← 外层横切
  │
  ▼
Handle / HandleContext 包装的 http.HandlerFunc
  ① gctx.NewContext（仅 HandleContext）→ 解析 traceparent / 生成 trace+span ID
  ② Bind()      —— Binder 自定义 or JSON body 解析        （framework/bind.go）
  ③ validator   —— 按 json tag 校验 Req                   （framework/handler.go）
  ④ 业务 handler → 返回 (*Res, error)                     （你的代码）
  ⑤ err==nil ? WriteOK(res) : WriteError(err)             （framework/response.go）
        └─ BizError：{业务码 code, HTTP 状态码, message}
        └─ 其他错误：500 + 统一"服务器内部错误"
  ▼
JSON 响应 {code, message, data}
```

## 七、设计原则

1. **小包独立**：errors/config/logger 无项目内依赖，可单独抽取使用；模块间依赖最弱化（gctx→logger 仅 key 常量）
2. **不重复造轮子**：不做路由（推荐 chi）、不强制 OTel、错误与标准库兼容
3. **context 作为唯一通道**：日志链路字段通过 context + key 契约传递，包间不 import 对方实现
4. **简洁优先**：不提供 kv 字段日志、不提供中间件链，用到再加
5. **失败要显式**：config 重复 key panic、gctx 重复 Set panic，宁可启动失败不静默覆盖
