# 日志结构 OTel 对齐与手写编码器方案

创建日期：2026-09-21（周一）

## 目标

1. 日志字段命名与嵌套结构**对齐 OTel**（Logs Data Model + Resource 语义约定）
2. 引入全局 resource 字段与完整的配置优先级体系
3. 为**手写 JSON 编码器**铺路：先把 schema 定稳，再实现编码器（避免结构反复变更导致编码器重写）

## 背景

性能对比显示，本库 JSON 编码是最大短板（同机、`io.Discard`、等价日志内容）：

| 库 | JSON | JSON + caller |
|---|---|---|
| zerolog | 49 ns | — |
| zap | 192 ns | 506 ns |
| slog | 326 ns | 815 ns |
| logrus | 1168 ns | — |
| **go-gear（现状）** | **2506 ns** / 25 allocs | **3737 ns** / 29 allocs |

瓶颈为 `map[string]any` + 反射 `json.Marshal`（含 map 键排序）。主流库均采用手写编码器 + 零分配。手写编码器会把结构写实在拼接代码中，**因此必须先固化 schema**。

## 方案设计

### 1. 字段命名（对齐 OTel）

| 原字段 | OTel 对齐名 | 说明 |
|---|---|---|
| `time` | `timestamp` | OTel Timestamp |
| `level` | `severity_text` | OTel SeverityText |
| `msg` | `body` | OTel Body |
| `caller` | `code.filepath` + `code.lineno` | OTel 代码位置语义约定（拆两个字段） |
| `root_trace_id` | `trace_id` | OTel TraceId |
| `current_span_id` | `span_id` | OTel SpanId |
| `middle_span_ids` | `parent_span_ids` | 项目扩展（OTel 无对应，保留） |

### 2. 嵌套结构（严格 OTel）

自定义键值对**归入 `attributes`**，采用**对象形式**（OTel 数据模型 Attributes 本身即 map；可读、可查、体积小。OTLP 传输层的 KeyValue 数组仅在直接当 OTLP 解析时需要，而 OTLP 链路已由 `middleware.OTel` 承担）：

```json
"attributes": {"user_id": 123, "source": "api"}
```

Resource 字段**嵌套在 `resource`**：

```json
"resource": {"service.name": "user-api", "service.version": "1.2.0",
             "deployment.environment": "prod", "host.name": "node-1"}
```

### 3. 时间格式

RFC3339 带时区偏移 + 固定微秒精度（人读友好、可辨时区、精度足够）：

```
2026-09-21T10:30:00.123456+08:00
```

Go layout：`2006-01-02T15:04:05.000000Z07:00`（不用 `RFC3339Nano`，避免尾随零不一致）。手写编码器可用"缓存到秒的日期前缀 + 拼微秒/时区"加速。

### 4. 全局字段与配置优先级

| resource 字段 | 来源 |
|---|---|
| `service.name` | 配置 |
| `service.version` | 配置 |
| `deployment.environment` | 配置 |
| `host.name` | 配置，默认取 `os.Hostname()` |

**优先级（低 → 高）**：代码兜底值 < 配置文件 < 环境变量 < 命令行选项。
- config 包负责 file → env 覆盖；命令行选项（最高）**待实现**
- logger 只接收最终值，不感知来源

### 5. 输出顺序（手写编码器固定此序）

```
timestamp → severity_text → body → code.filepath → code.lineno
→ trace_id → span_id → parent_span_ids
→ resource{service.name, service.version, deployment.environment, host.name}
→ attributes{...kv}
```

固定字段在前，动态 kv 在 `attributes` 内按调用顺序输出。

### 6. middle span 表示（链表存储 + 读取聚合）

**现状（gctx）**：

| 层面 | 方案 |
|------|------|
| 存储 | **链表**：`Context.parent *Context` 父指针链，`StartSpan` 仅设 parent，追加 O(1)、无数组拷贝 |
| 读取 | **动态聚合成切片**：`MiddleSpanIDs()` 递归父链 append 为 `[]string`，时间复杂度 O(d²)，每次取链都重算 |
| 日志侧 | `traceInfo` / `entry` 均为 `[]string`，JSON 输出数组 |
| 残留 | `ctx.middleSpanIDs []string` 字段从未赋值，属死字段，待清理 |

**本方案做法**：保留链表存储；日志条目生成“从根到当前”的有序数组，编码器遍历写出 JSON 数组。

**默认关闭（性能优先）**：增加配置项 `ParentSpanIDs bool`（默认 `false`）——关闭时**不读取** `MiddleSpanIDsKey`，因而完全不触发 `MiddleSpanIDs()` 的聚合与切片分配；开启后才输出 `parent_span_ids`。

**顺带优化**：`MiddleSpanIDs()` 改为单次迭代（O(d)）+ 删除死字段。

### 7. 重名策略

**内置字段优先**：自定义 kv 与内置字段（含 resource 字段名）重名时**跳过自定义字段**，防止内置字段被覆盖成错误类型导致序列化异常。
