# 日志追踪链路打通方案

创建日期：2026-09-02（周三）

## 目标

打通 gctx（请求上下文，持有 traceID / spanID）与 logger（日志输出 trace 字段）的链路：业务代码 `logger.Info(ctx, ...)` 自动携带 trace ID，且 gctx 与 logger 两个包之间**不互相耦合**。

## 背景

- `gctx.Context` 的 traceID 存在**独立字段**中，从未写入标准 `context.Context`
- `logger` 通过 context key 读取 traceID，但两包各自定义了不同的 key 类型
- 断点有两个：① 值没进 context；② 读取方与注入方的 key 不共享

## 方案设计（候选与取舍）

| 方案 | 依赖方向 | 结论 |
|------|---------|------|
| A：key 收敛到 gctx，`NewContext` 注入下沉 | gctx ← logger（logger 依赖 gctx） | 破坏 logger 独立性 |
| B：gctx 注入 logger 的 key | gctx → logger | 依赖方向反直觉，未采用 |
| C：framework 粘合注入 | framework 依赖两边 | 只覆盖 framework 入口 |
| **D：接口契约** | **无依赖** | **选定** |

选定方案 D：logger 作为契约方定义 `TraceIDProvider` 接口（`TraceID() string`），`traceIDFromCtx` 双路径读取（先查 key 注入，再断言接口）。gctx.Context 已有 `TraceID()` 方法，天然满足契约，**三方零新依赖**。

## 结论

采用远程 `e568044` 的 trace 设计，不自研接口方案：

- **logger 只读**：定义 `RootTraceIDKey` / `MiddleSpanIDsKey` / `CurrentSpanIDKey` 三个 key 作为唯一契约
- **数据方动态提供**，按场景二选一：
  - 不接 OTel：`gctx.Context.Value()` 识别 key，动态返回自身 traceID / spanID，`middle_span_ids` 从父链实时聚合
  - 接 OTel：`middleware.OTel` 将 OTel span 的 ID 经 `WithRootTraceID` / `WithCurrentSpanID` 注入 context
- 远程方案支持 **span 链**（middle_span_ids 数组），比单 traceID 的接口方案更完整，故放弃本地实现

教训：本地开发前应先同步远程（`git fetch` + 检查分叉），避免在已被远程取代的设计上重复投入。

## 遗留问题

- OTel 与 gctx 两套 ID 来源并存：上游无 `traceparent` 时各自生成 ID 可能不一致。**用法约定：接 OTel 的入口用 `Handle`，不接 OTel 用 `HandleContext`**
